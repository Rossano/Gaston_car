# GEMINI.md - Gaston_car Firmware Analysis

This document provides a comprehensive overview of the `Gaston_car` firmware project, intended to serve as a detailed context for Gemini.

## Project Overview

This is an embedded C project for the Silicon Labs **EFR32BG22C224F512IM40** microcontroller. The project is named `Gaston_car`, suggesting its application in a remote-controlled vehicle.

The core functionality of this firmware is a **Bluetooth Low Energy (BLE) to Serial Bridge**, commonly known as a Serial Port Profile (SPP). This allows for wireless communication between a host (like a smartphone or computer) and the microcontroller's serial port (EUSART).

The project is built upon the Silicon Labs Simplicity SDK and utilizes the **FreeRTOS** real-time operating system to manage tasks.

### Key Features:

*   **BLE Peripheral:** The device advertises itself and allows a central device (e.g., a phone) to connect.
*   **Serial Port Profile (SPP):**
    *   Data received from the host via BLE is written to the microcontroller's serial output (VCOM).
    *   Data received on the serial input (e.g., from another on-board system or typed in a terminal) is sent to the host via BLE notifications.
*   **Task Management:** Uses FreeRTOS to manage a dedicated task (`cli_task`) for handling the bidirectional serial communication, ensuring non-blocking operation.
*   **GATT Service:** Implements a custom GATT service with a writable characteristic (`My_SPP_Write`) that is used for the SPP data transfer. The "SPP mode" is activated when a client subscribes to notifications for this characteristic.

## Code Structure

*   `app.c`: Main application logic, including Bluetooth event handling (`sl_bt_on_event`) and initialization of the FreeRTOS CLI task. It manages the state of the BLE connection and forwards incoming BLE data to the serial task.
*   `spp.c`: Contains helper functions for the SPP service, notably `send_spp_data` which sends data over BLE to the connected host.
*   `cli.c`: Implements the `cli_task` which runs in an infinite loop. This task is the heart of the SPP bridge, polling both the serial port for input to send over BLE and a queue for BLE data to write to the serial port.
*   `main.c`: The C entry point for the application.
*   `autogen/`: Contains files automatically generated by the Simplicity Studio IDE, including GATT database definitions (`gatt_db.c`, `gatt_db.h`) and Bluetooth stack initializations.
*   `config/`: Contains various configuration files for the Bluetooth stack, peripherals (like EUSART), and RTOS.
*   `cmake_gcc/`: Contains the build system files for compiling with GCC and CMake.

## Building and Running

### Build Process

The project is configured to be built using **CMake** and **GCC for ARM**.

1.  Navigate to the `cmake_gcc/build/` directory.
2.  The presence of `CMakeCache.txt` and ninja build files (`.ninja_log`, `build.ninja`) indicates the build system has been configured.
3.  To rebuild the project, you would typically run `cmake --build .` or `ninja` from within the `cmake_gcc/build` directory.

The main build configuration is defined in `cmake_gcc/CMakeLists.txt`, which in turn includes `bt_soc_gaston.cmake` (likely generated by Simplicity Studio) for specific source files and flags.

### Flashing the Firmware

The build process generates several output formats in `cmake_gcc/build/base/`:

*   `bt_soc_gaston.hex` (Intel Hex format)
*   `bt_soc_gaston.bin` (Raw binary)
*   `bt_soc_gaston.s37` (S-record format)

These files can be flashed onto the EFR32BG22 target hardware using a J-Link programmer and appropriate flashing software (e.g., J-Flash, Simplicity Commander). The `.jdebug` file suggests that Segger J-Link tools are used for debugging.

## Development Conventions

*   **RTOS-based:** The application is event-driven and uses FreeRTOS tasks and queues for concurrency and to prevent blocking operations, especially in the Bluetooth event handler. For example, incoming BLE data is placed in `uartQueue` to be processed by the lower-priority `cli_task`.
*   **Modular:** Logic is separated into different files (`app.c`, `spp.c`, `cli.c`) based on functionality.
*   **Silicon Labs SDK:** The code extensively uses APIs from the Silicon Labs Bluetooth stack (`sl_bt_*`) and peripheral drivers (`sl_iostream_*`).
*   **Logging:** `app_log` is used for debug messages, which are output over the VCOM port.
